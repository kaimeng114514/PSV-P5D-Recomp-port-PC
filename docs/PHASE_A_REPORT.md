# P5D 完美 60fps 阶段 A 可行性报告（go/no-go）

日期：2026-11-10 · 范围：阶段 A（不改正式发布，60 选项保持实验性）· 结论：**GO（有条件）**

## 1. 结论

**继续进入阶段 B 在技术上是可行的（有条件 GO）**，但不是靠运行时开关/钩子能完成的：需要引擎级"逻辑与呈现解耦 + 动画时间 dt 化"。

- **支持 GO 的证据**
  1. 引擎的动画求值层使用**浮点时间**：`appCalculator` 关键帧系统（主求值 `appCalculator_81154b9c`、插值 `fn_81154e1c`、缓动插值 `fn_8116490c`、缓动助手 `fn_81154e06` 259 个调用点）输入是浮点时间，可表示分数帧。
  2. 主菜单 3D 背景/相机的动画代码直接调用该浮点关键帧求值器：`mainMenuBG_P3_810f5256`、`mainMenuCamera_P3_810f7708`、`mainMenu_P3_810fc208`（均出现在关键帧主求值器的 11 个调用者中）。
  3. 3D 模型更新入口 `appGxModel`（`fn_810059a4`）接收到的是**真实帧时长浮点参数**（30fps 时实测 s0≈0.0333，60fps 时≈0.0174），说明模型层入口已有 dt 概念。
  4. 舞池的音乐/判定时钟在 60 帧下已验证为真实时间（每 60 帧 1.0000s，同路线舞蹈总时长一致）。

- **限制 GO 的问题（阶段 B 必须解决）**
  1. 序列/任务（title job、菜单状态机、appMovie/job 时间）是**按呈现帧号**推进的：标题 job 状态在 30fps 与 60fps 下落在相同帧号（79→83→332 vs 80→84→333）；job 时间 = 呈现帧号/30（60fps 下每秒 +2.0）。
  2. 运行时钩子尝试全部失败（13 处 1/30 常量 frame_dt、appMframe 60 基、job-wait 参数缩放、vblank 回调节流、舞池 4 站点 frame_dt），其中舞池站点替换反而使 3D 每帧变化从 13.5 飙到 45.5（动画扭曲）。
  3. 把 job 时间 getter 在 60 帧下减半（RECOMP_P5D_JOBSLOW=1）后，主菜单 3D 每秒变化只从 873 降到 770（30fps 基线 324，约 -12%），说明还有其它帧号驱动。

## 3. 阶段 B 建议路线（需要新批准）

1. **M-B1**：在 appCalculator 关键帧求值器入口注入"dt 化的浮点时间"（60fps 下每帧推进 1/60s 的动画时间），先覆盖主菜单 3D 背景/相机，验收"每秒画面变化与 30fps 基线一致 + 每帧变化约一半"。
2. **M-B2**：把棋盘/谱面驱动的帧号系统（title job 步进、job/movie 时间）改为真实时间基准；验收标题序列时长恢复 ~4.1s（60fps 下）。
3. **M-B3**：逻辑/呈现解耦：30Hz 帧号逻辑 + 60Hz 呈现 + 场景插值（骨骼矩阵插值或更高层场景状态插值），逐场景接入（主菜单→舞池→剧情→观察）。
4. **M-B4**：整链路验证（RECOMP_METRICS speed≈1.0、fps=60、音乐/判定/动画时长一致）→ 60 选项转正 → 重新打包发布。

风险：M-B2/M-B3 工作量大、部分系统可能无法完全还原（镜头/特效可接受 30Hz 步进）；不保证全部场景达到"完美"。
